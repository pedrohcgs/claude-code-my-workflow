## Hook layer qualification (2026-08-23)

consumes, and when it stops working it stops working **silently** — no error, no red gate, just a
session that behaves as though the hook had nothing to say. Two checks now stand behind that:
gate 9 (`check-ledger-coverage.py`) proves every hook is *wired* to a file that exists, and gate
10 (`hook-battery.sh`) proves the wired file still *acts* — it re-seeds each guard's target
failure on every backtest run, so the three guard rows below are re-measured continuously, not

> **Disclosed residual on `git-guardrails.py`'s clean-tree check (r8, narrowed at r9).** The
> check no longer PREDICTS anything, so the residual is a list of forms it cannot SEE, not a
> list of semantics it might mis-model.
>
> **What it guarantees — this much, and no more (rewritten at r13).** For a history op the
> parser IDENTIFIES, the op must first be a STANDALONE SIMPLE COMMAND or it is denied outright;
> then, if it carries no escape token, the verdict is a LIVE `git status --porcelain` reading
> taken at hook time in the directory the invocation names. Nothing in the command text
> substitutes for that reading, so the ALLOW side is reachable only by a tree that is actually
> clean — or by the op never being identified at all. **Before r13 the first clause did not
> exist, and the guarantee was therefore only “the parser-selected repository was clean when
> the Bash tool call was authorized”** — materially narrower than the “starts from a
> clean tree” that the docstring summary and law 20 asserted. The standalone rule is what
> makes the reading mean anything, because it removes every command shape that could act
> between the reading and the op.
>
> **What it does NOT guarantee, stated because r9 falsified the previous wording:** that it
> identifies every shell form. It does not, and no version of it will. Identification is a
> best-effort textual parse of the command line, and it is the whole of what stands between an
> op and the reading. Where the parse can go either way the code is written to fall toward
> finding an op — an unknown git global option is consumed rather than mistaken for the
> subcommand, a `git` word later in a segment is still searched for, a `-C` directory that
> cannot be read as a repository denies since r13 rather than falling back to the event cwd
> (c37/c38, control c39) — but "falls toward deny where the parse permits"
> is not "denies everything it should". **A form the parser does not identify is not denied; it
> is invisible, and the op runs.** Those forms are listed below, and the list is a report of
> where the parser has been probed, not a proof of where it is complete.
>
> What it does NOT see: a history op carried by an interpreter (`python3 -c
> '...subprocess.run(["git","merge"])...'`); one inside a shell-wrapper payload (`bash -c 'git
> merge main'`, `env -S 'git pull'` — `root-of-trust-guard.py` DOES unwrap those payloads, and
> since r14 it routes each one through this hook's `git_deny_reason()`, so a **destructive**
> verb in a payload is now caught (battery a31-a38). Only that half is shared: THIS check —
> the clean-tree precondition — does not unwrap
> `-c` payloads; more generally, an op that survives quoting as a single WORD is one word to the
> tokenizer); one run from an alias, a script file, a Makefile target, or a git hook; a

## Round 17 (2026-08-24) — three classes, and two of them are about the record, not the code

Audited at `c285699`. Three confirmed findings, and what makes the round worth its own section is
that **two of them are failures of the previous round rather than of the original design**.

**1. A NEW FALSE-ALLOW, INTRODUCED BY THE LAST ROUND'S OWN FIX — `_heredoc_opener` was blind to
shell comments (blocker).** r16 rewrote the heredoc opener scan to be quote- and
herestring-aware, and disclosed EXACTLY ONE surviving misread (`$(( x << n ))`). It had a second:
the walk had no notion of a shell COMMENT, and `strip_heredocs` runs BEFORE the comment-aware
segmenter, so a line-one comment merely NAMING a heredoc (`# heredoc <<EOF`) invented a terminator
and DELETED every following line — silencing the entire deny spine of BOTH guards while bash ran
those lines normally. Measured, and executed rather than simulated: `bash -c` on the two-line form
left the guard file absent. Fixed, pinned by a65/a66/b21/b22 with controls a67/b23, and qualified
by seeding in both directions (see the reproduction paragraph in the hook section above). **The
lesson for this ledger is the one r16 already claimed to have learned:** a residual list is a
claim about what a fix misses, and this one was wrong at the moment it was written. A disclosure
that has not been probed is a hypothesis, not a boundary — the r17 seeds are what make the new
disclosure (still `$(( x << n ))`) worth more than the old one.

**2. A FIX DECLARED IN THE RELEASE RECORD AND NEVER MADE (blocker).** `c285699`'s commit message
states as landed work that the root-of-trust docstring's filesystem-expansion description was
corrected. `git show c285699 -- .claude/hooks/root-of-trust-guard.py` contains **no docstring
hunk**: the file still said the glob token "is expanded against the filesystem", that "`glob.glob`

with each other; only the docstring disagreed — and the docstring is the surface the guide and

filesystem call), the dotfile rule is attributed to the explicit check in `_segment_matches`
rather than to a `glob` semantic, and the note recording that the `glob.glob` design was tried

not by memory of having edited it**, which is precisely the check the previous round skipped.
**This one is NOT gated.** No checker compares a docstring against the code it describes, which
is how the sentence survived a declared fix for two rounds. Recorded here as visible debt rather
than quietly repaired: see the open item below.
